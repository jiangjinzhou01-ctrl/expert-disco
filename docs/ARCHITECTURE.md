# G0 架构

本文件描述已实现的模块边界和技术设计，行为是否通过验证以验收表及对应执行证据为准。

## 所有权与状态

| 模块 | 职责与约束 |
| --- | --- |
| `PortalMath.ts` | 纯 Three.js 数学；不访问 DOM、React、WebGL 或 Rapier。验证刚体门姿态，生成映射、方向和交点。 |
| `PortalRegistry.ts` | 显式门和双向连接拓扑；拒绝重复 ID、错误世界与无效门尺寸。 |
| `PortalGeometry.ts` / `RoomA.tsx` / `RoomB.tsx` | 构造两个独立 `Scene`；几何门洞用共享房间描述生成，图形墙面与物理墙体保持同源。 |
| `PortalRenderer.ts` | 虚拟相机、出口裁剪、单个 Render Target、离屏绘制和图形资源生命周期；不改变玩家物理归属。 |
| `PlayerState.ts` | 可变高频玩家位置、四元数、速度、世界 ID、地面和模拟步信息；不逐帧写 React state。 |
| `PhysicsRuntime.ts` / `CollisionQueries.ts` | Rapier 世界、运动学胶囊、静态房间碰撞与出口形状查询。 |
| `PlayerController.ts` | 输入驱动速度、重力、地面和碰撞修正；不控制门内画面。 |
| `PortalTransfer.ts` | 唯一检测并原子提交空间转移的模块；记录拒绝原因与唯一事件编号。 |
| `ExperienceLoop.ts` | 唯一核心模拟和渲染调度所有者。 |
| `Diagnostics` | 低频读取已提交状态，保存性能与传送记录；不影响正式模拟结果。 |

React 建立画布和低频 UI。R3F 的单个 `useFrame(callback,1)` 正式接管自动渲染；禁止第二个 RAF 或独立 Rapier 定时步。UI 轮询不拥有模拟时间。

## 空间约定与几何

右手坐标系，单位米，世界 +Y 为上。门的局部 +X 为右、+Y 为上、+Z 为正面。玩家中心从门局部 `z>0` 到 `z<=0` 的运动才构成正向进入，目标从局部 +Z 离开。

门仅支持平移和绕世界 Y 轴旋转；不支持缩放、镜像、倾斜或滚转。数学模块明确拒绝 NaN、Infinity、非单位四元数、奇异/剪切/缩放/反射/非仿射矩阵，防止非法数据向渲染与物理传播。

A 门为 `(0,1.45,-8)`，朝向 +Z；B 门为 `(32,1.45,0)`，绕 Y 旋转 π/2。两个独立 Scene 的坐标对应统一 Rapier 世界中不重叠的区域。房间约 16×16×6m。

门洞宽 2.4m、高 2.9m，原点在中心。门所在墙拆为左右、顶部独立 box，框条也具有真实碰撞体，没有跨越整个门洞的隐形墙。地板和建筑 box 来自 `RoomLayout.ts`。

玩家胶囊半径 0.30m、总高 1.74m；Rapier `capsule` 的圆柱半高为 `(1.74-2×0.30)/2=0.57m`，不是 0.87m 或 1.74m。玩家状态位置是胶囊中心；相机偏移为眼高 1.55m 减中心高度 0.87m，即 +0.68m。

## 数学映射

令源门和目标门世界矩阵分别为 `M_A`、`M_B`：

```text
T_AB = M_B · Ry(π) · inverse(M_A)
T_BA = inverse(T_AB)
p_B = T_AB · [p_A,1]
v_B = R_AB · v_A
q_B = q_AB · q_A
```

位置使用齐次坐标；速度和输入向量只施加旋转，不使用平移或归一化。`T_BA` 也会与反向直接构造 `M_A·Ry(π)·inverse(M_B)` 对照。合法变换保持距离与速度模长，重力始终为世界 -Y。

穿越使用物理步内的实际运动线段。若前后有符号距离为 `d0>0`、`d1<=0`，则 `t=d0/(d0-d1)`，交点为 `lerp(start,end,t)`。近平行或微小分母被拒绝。门洞检查在源门局部空间进行，左右扣除胶囊半径、上下扣除胶囊总半高。

## 实时图形流程

1. 从已提交玩家状态更新主相机。
2. 使用 `T_AB` 映射相机世界矩阵，虚拟相机复制主相机投影参数与矩阵。
3. 创建目标出口的世界裁剪平面，保留目标局部 +Z 一侧。
4. 临时隐藏目标门表面，以避免递归；保留目标建筑与参考物。
5. 将目标 Scene 绘制进唯一 Render Target。
6. 在 `finally` 恢复 target、viewport、scissor、clipping、clear、XR、shadow、目标门可见性与 info 状态。
7. 绘制源 Scene，门洞表面以 `gl_FragCoord.xy / drawingBufferSize` 采样实时目标纹理。

门表面是一块正确尺寸的平面并参与深度测试，墙面、门框与普通几何遮挡它。顶点shader把仍在眼前的门面深度限制在近裁剪面内，避免眼睛距门平面仅5mm时门面因near裁剪消失；它不是全屏覆盖层。Render Target 和主画布保持相同宽高比，质量系数只改变采样分辨率，不改变透视。每帧最多一个离屏 pass，无递归或静态假图像。

RT 使用 `setSize()` 在尺寸变化时重分配，重复帧不新建 RT。场景几何和材质复用，销毁时去重释放；上下文事件由渲染模块观测和恢复。具体生命周期测试状态见验收表。

## 固定步与原子传送

核心顺序：读取输入 → 固定步累积 → 原始候选位移 → 按无限门平面切分 → 仅源平面前段碰撞 → 实际交点/胶囊门洞复核 → 目标胶囊空间与剩余扫掠查询 → 目标剩余位移碰撞 → 原子映射/提交Rapier与玩家状态 → 相机/实时门绘制 → 诊断采样。

`PlayerController`把raw desired位移交给`PortalTransfer`，源角色查询只能接收平面前段；不能先用源世界求解完整位移，再把已被源门后障碍削减的剩余量传给目标。前段实际运动未到门面时，停留源世界继续下一物理步；如果无名义跨面但碰撞偏转却越过平面，保守拒绝到安全源位置，不能无事件进入门后。

胶囊体积会先于中心伸过门面。因此近门普通运动与源前段查询会剔除完全位于源门背面的建筑cuboid；与门平面相交的门框/墙体保留。每次query前预计算被排除的handle集合，Rapier查询callback只读取JS元数据/集合，不在WASM借用期间再次调用collider访问器。目标胶囊overlap与sweep不使用这项剔除，仍检查完整目标空间。

物理目标频率 60Hz，并限制长帧最大追赶步数，避免浏览器无限补算。普通位移与跨 40m 的瞬时重定位分开提交，防止生成不合理的运动学速度。跨世界不能把位置按普通线性插值连接。

传送状态基于空间和方向重新武装，不使用固定一秒冷却：`ARMED → CROSSING → TRANSFERRED → WAITING_FOR_REARM → ARMED`。每物理步最多一次成功事件；唯一递增编号用于测试和诊断。

出口查询过滤自身、考虑完整胶囊、允许合法地面接触并检查剩余路径。锚点重叠或剩余扫掠路径遇到非地面障碍时，G0选择保守拒绝整次传送，退回源侧安全距离；不会先把角色塞进目标墙再纠正。通过查询后由目标区域角色控制器处理剩余位移，源控制器不处理目标段。实现与行为由 P01–P09 集成测试验证。

## 验证边界

数学属性测试采用固定种子 `0x54485245`，至少 1000 组随机姿态。视觉测试使用固定 Chromium、1920×1080、DPR 1，并将已知标记坐标的独立投影与真实像素中心对比。截图辅助定位错误，不能代替矩阵、物理状态与传送事件断言。

诊断快照深拷贝事件记录与数组，并复制渲染指标，避免后续传送污染先前采样时间点。

测试变更接口仅用于 `DEV` 或明确 `e2e` 构建模式的 `?test=1` 入口；普通生产构建只保留正式输入和按需只读诊断。软件渲染器上的帧率只代表测试环境，不能作为 Android 性能验收。
