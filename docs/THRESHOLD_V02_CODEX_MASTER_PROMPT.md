## 3. 坐标与几何唯一有效基线（CR1）

采用 INVERT **局部**右手坐标：`+Y` 向上，玩家入门后主要沿 `-Z` 方向探索；单位米。局部坐标要通过场景根矩阵映射到 G0 物理世界，**不要误把不同场景局部坐标直接当成 G0 全局位置**。根据 `CR1` 读取并验证具体数据；如本正文与 CR1 原始 manifest 精度有出入，manifest 数值优先，但要用代码验算，不盲从不合理字段。

**INVERT 包围盒**：X[-15,15]、Y[0,22]、Z[-19,19]；局部视觉下沉区域可达 Y=-7，但非主要玩家道路。入口门中心 `(0,2.8,+18.2)`，正面法线世界局部 `-Z`，洞口净宽3.6、高5.6，下边缘Y=0。**与前厅入口门通过现有 portal 映射形成相容朝向和可逆双向穿越。**

**前厅 VESTIBULE**：中庭设计范围 X[-16,16]、Z[-22,22]、Y[0,24]；入口走廊约宽4、长14、高5，Z[+22,+36]；下沉区域 X[-5,+5]、Z[+2,+10]、深4；主门外框 6m×8m，实际通行净洞 3.6m×5.6m、底部Y=0。入口玩家从 +Z 朝 -Z 前进；前厅主门应面向玩家并与 INVERT 端口对位，具体门中心朝向按接入 G0 的世界变换精确计算，不能把外框中心高度和净洞中心高度混淆。中庭必须存在可行走的绕行路线、可见下沉负空间和有真实结构厚度的悬挑廊桥。

**重力弧面**（最重要）：半径R=3.2；沿 Z 方向展宽到 `[-9,-5]`，参考路线 Z=-7。角度 `θ∈[0,π/2]`，脚底接触点：

```
x = 1.5 + 3.2*sin(theta)
y = 3.2*(1-cos(theta))
z ∈ [-9,-5]
localUp = (-sin(theta), cos(theta), 0)
g = -9.81 * localUp
```

弧面的起点 `P3=(1.5,0,-7)`，终点 `P4=(4.7,3.2,-7)`；终点切线沿 `+Y`，再**真实沿墙走 0.8m**到 `P4A=(4.7,4.0,-7)`，然后转向 `-Z`。地面→弧面→墙面应位置、切线与物理接触连续；**视觉网格与碰撞网格由同一数学曲线生成**，弧面至少64角度段起步，不能用两个重叠共面的独立碰撞面制造接缝。

**角色**：胶囊半径0.30、总高1.74；脚底到胶囊中心0.87；脚底到眼睛1.55：

```
P_body = P_foot + 0.87*localUp
P_eye  = P_foot + 1.55*localUp
```

例如 θ=45°：脚底≈(3.7627,0.9373,-7)，眼睛≈(2.6667,2.0333,-7)；θ=90°：脚底(4.7,3.2,-7)，眼睛(3.15,3.2,-7)。**胶囊长轴、相机局部 Up、移动切平面和接触法线必须保持一致**。

**墙面**：支撑平面 X=4.7，墙面可行走参数范围 Y[3.2,7.2]、Z[-18.2,-5]；墙面主路线 Y=4.0，沿 Z 从 -9 到 -16.5；终端实体保护边界 Z=-18.2。新重力朝 +X，角色局部向上为 -X。保护构件必须真实可见、具有实体碰撞，不得隐身。弧面后过渡段与墙面不要存在重复相交的共面碰撞支持面。

## 4. 进入正式建模前必须关掉的三类空间风险

**必须在同一次执行中完成 CR1 灰盒物理验收，不能只输出验证建议并停止**：

1. **接缝**：生成同源弧面碰撞体；在 0°、5°、15°、30°、45°、60°、75°、85°、90°、以及 P4→P4A 处测试身体完整形状的位移与姿态扫掠、停止/倒退/斜走；不能只检查胶囊中心或相机。接触法线保持稳定，不能穿入墙面、卡进护墙或在接缝被弹飞。胶囊沿弧旋转不是 Rapier 角色控制器自动支持的能力，需自行实现旋转与重叠/路径查询。如果物理碰撞需要微小的网格、窗框或角色控制容差修正，只允许记录最小偏移，保留核心弧面半径、角度和 P3/P4/P4A 逻辑。

## 5. 真实重力与玩家系统实施

- 从 G0 的直立胶囊版本升级到支持任意局部 Up 的运动学角色；保留原 G0 模式与正常重力能力。
- 物理时间步固定 1/60s、单一调度所有权；渲染相机从已提交快照生成，跨世界状态切换不允许在不相关坐标间插值。
- 使用弧面接触点或可靠最近支撑查询确定 θ 与 localUp；加重力切换滞回，避免接触边界的数值噪声造成方向震荡。
- 对运动输入建立相对于局部 Up 的前/右基向量；向前摇杆要沿弧面切线真实行走，不能投影回原世界水平面。走上墙后沿 -Z 行走；仍允许停止、倒退和反向返回。
- 使用四元数更新角色姿态；真正旋转胶囊碰撞体，执行分段旋转形状查询/重叠检查，防止在弧面内穿帮。不能保持 `lockRotations()` 然后单独旋转摄像机冒充正确。
- 将相机眼睛定位在真实脚底 + 1.55*Up 处。滚转/观察输入随局部 Up 变化；减少运动模式可以调整镜头角速度、转场感受，**不改变身体真实姿态或重力规则**。
- 角色重力和异常物体重力独立，不把 INVERT 全世界全局重力一键切换。明确选择“全局重力为零 + 每体受力”或“正常世界全局 -Y + 指定物体差分补偿”策略，避免重力叠加或遗漏。
- `DYNAMIC_WITNESS` 黑色物体必须在可见区域横向落向侧墙，受到真正的局部重力与碰撞约束，不只是关键帧移动；装置与玩家终点状态机可用低成本确定性动画。
- 角色在新重力场进入传送门之前，需先恢复正常世界的 -Y 重力和姿态；主门户位于正常重力区域，不要让侧躺的胶囊传入 G0 原本只支持 yaw 门的系统。
- 容错：最近有效检查点、零速度安全重定位、NaN 防御、碰撞异常记录、斜向输入限幅、失焦与触控取消恢复。

## 6. 美术品质：明确禁止“几个放大的 BoxGeometry”

视觉目标：**纪念碑式极简建筑 + 当代装置艺术 + 具有空间逻辑的超现实**，不是商业酒店大堂、普通展览样板间，也不是科幻霓虹隧道。第一眼应看到厚重的建筑、巨大空间的光影和真实的负空间；第三镜头应看见方向矛盾，绝不能只是一条普通走廊。

**VESTIBULE** 必须具备：长度14m的压缩入口廊、渐次显露的24m高主中庭、32×44m左右的体量、4m深中央下沉空间（有可见栏杆和绕行）、左右错层悬挑廊桥、厚重立柱和墙面切口、顶部自然采光长缝、真实8m高大型深黑门框与3.6×5.6m可穿越净洞、真实建筑台阶/过渡，以及玩家完成 INVERT 后有明确变化的中央几何装置。不能将大门做成一块黑色矩形贴在墙上。

**INVERT** 必须具备：冷灰巨构的正常入口区域、交叉建筑方向参照、真实弧面及其有厚度的围护、可碰撞的观察窗、侧向重力物体、完整可行走墙面路线、终点装置和可返回通路。**CAM-03 的形体感必须比单张漂亮走廊图更重要。**

门框黑曜石不是夸张镜面，也不应到处堆金色栏杆。微表面孔隙、细小倒角、粗糙度变化与建筑接缝可见，但不得以大面积脏污噪声/随机裂纹假装复杂度。所有重要墙体必须有实际厚度，门洞有真实内侧衬口和遮挡。

**光照**：前厅顶部窄缝自然主光（偏中性、约5600K）与有节制的环境反弹，光区聚焦门前地面和一侧墙面；INVERT 用来自侧向切口的较冷定向光，展示未旋转的原始建筑关系。优先离线烘焙静态间接光，移动物体允许少量实时近似阴影。禁止满屏 Bloom、廉价发光轮廓和不明来源的强烈点光。保持统一色彩管理、曝光和 tone mapping。

**资产落地**：必须创建并交付实际可维护的 3D 几何资产，不许仅生成效果图。首选可脚本化且可复现的 Blender 源文件/导出流程（Blender 可用则利用 headless）；导出标准 GLB/glTF，使用可复用 Mesh/材质、场景模块与独立碰撞代理，并提供资产 ID、原点、包围盒、材质、三角面数、所属场景的 manifest。若环境无 Blender，则采用**可复现的参数化建筑几何生成器**创建具有厚度、切口、桥梁、楼梯、凹槽与倒角的真正结构模型，并导出或纳入引擎，不能以一堆未经设计的 BoxGeometry 充数。遇到复杂材质/烘焙能力限制，诚实记录并采用可运行的 PBR/程序化纹理替代，不得把未生成的 `.blend`/`.glb` 写作已交付。

正式场景应有实质性变化：不能仅修改背景色、添加纹理和 Bloom 就宣称 V0.2 视觉升级完成。保留 `G0-LAB` 诊断模式、但正式入口默认展示完整前厅。

## 7. 建筑与游戏玩法的统一

- **建筑形体与碰撞代理分离但同源定位**：视觉高精网格不等同于复杂动态刚体碰撞。每个通道、窗户、栏杆和门洞都要明确可通行/不可通行/仅可观察属性。
- 门的实际通行洞口与 PortalMath 的局部平面、正面法线、有效矩形必须一致；修改美术外框不改变世界映射数学。
- 从门外观察 INVERT 时必须显示真实目标场景，可从不同角度产生正确运动视差；穿越后的建筑、动态参照物和装置状态与门外观察一致。
- 出口遇到障碍必须做安全碰撞处理；优先改善 G0 保守拒绝整次传送的体验，但不得牺牲安全或破坏原先已验证的分段运动。边界问题必须新增回归测试。
- 到 P6 后玩家可主动触发终点装置；装置状态改变后返回路线始终可用，前厅中央装置发生克制的视觉变化。事件是玩家行为的反馈，不是自动强制剧情。
- 可以在新手首次进入时给短暂引导，但随时可操作；避免遮挡三维空间的大段 HUD、任务栏和长片头。

## 8. 手机与桌面完整对等

桌面：WASD + 鼠标视角，必要时 E 交互，Esc 释放，R 安全复位，F3 诊断。手机横屏：左手双区虚拟摇杆，右侧滑动观察，靠近装置才显示交互按钮；双指 Pointer ID 独立，支持 pointercancel、指针捕获、页面失焦与方向变化。屏幕边缘安全区、按钮可读性、触控滚动拦截必须正确。不可只允许手机“观看”。

墙面转换期间触控输入**仍需连续生效**，而不是播放无交互的旋转镜头；玩家能停下、倒退、顺利回到地面。提供普通/减少运动镜头选项，后者减少滚转突变但保留真实胶囊方向与碰撞。初始 50° 垂直 FOV 作为标志镜头设计基线，实际自由视角可按设备画幅配置；19.5:9、20:9 横屏至少完成自动化界面与遮挡检查。若浏览器不允许强制横屏，则优雅显示旋转建议，不崩溃。

## 9. 性能与资源约束

- 在门不可见或背对玩家时跳过无意义的 Render Target pass，近门保持正确实时更新；屏幕占比决定离屏分辨率，动态质量选项不改变玩法。
- 只有必要的静态/动态材质、贴图和几何；避免每帧 new 几何、贴图、Render Target；正确 dispose GPU 资源，处理上下文恢复。
- 静态场景资产合理拆分和预加载，避免在穿门瞬间才下载整个 INVERT；可评估 KTX2、Meshopt，但不要为压缩引入不可验证依赖。
- 目标：现代桌面 GPU 尽量 60fps，中端 Android 以 P95 帧时间≤33.3ms 的稳定30fps为验收目标。**指标是目标不是目前成绩**。原 G0 软件渲染报告约 14.36fps，不能拿它冒充硬件性能，也不应视为证明真机失败。
- 为首屏与后续场景建立真实资产传输体积预算，统计实际 JS/纹理/模型大小（不是只看源码大小）。能优化时优化，无法满足时报告真实结果。
- 性能诊断分别统计主场景/门内渲染开销、Draw Calls、P50/P95/P99帧时间、内存和资源数量。GPU Timer 不支持时显示 N/A。
